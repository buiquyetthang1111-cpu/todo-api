# Todo API

A RESTful API for managing a Todo list, built with Node.js and Express. Each todo has a state (`todo`, `doing` or `done`) and the API supports full CRUD with input validation and meaningful HTTP status codes. Data is kept in memory (a plain array), so it resets whenever the server restarts.

## Getting started

Requires Node.js 18 or newer.

```bash
npm install
npm start          # http://localhost:3000  (set PORT to change it)
npm test                  # all tests (unit + integration)
npm run test:unit         # unit tests only
npm run test:integration  # integration tests only
npm run test:coverage     # all tests with a coverage report
```

Interactive API documentation (Swagger UI, with *Try it out*) is at **http://localhost:3000/doc**. The raw OpenAPI document is `openapi.json`, also served at `/doc/openapi.json`.

On start, the server seeds one example todo ("Study REST APIs") so `GET /todos` is not empty.

## Data model

| Field         | Type                          | Notes                                                        |
| ------------- | ----------------------------- | ------------------------------------------------------------ |
| `id`          | string (UUID)                 | Generated by the server (`crypto.randomUUID()`), read-only   |
| `title`       | string                        | Required, non-empty, max 200 characters (trimmed)            |
| `description` | string \| null                | Optional, max 2000 characters                                |
| `state`       | `todo` \| `doing` \| `done`   | Optional on create (defaults to `todo`)                      |
| `dueDate`     | string \| null                | Optional ISO 8601 date (`2026-12-01`) or date-time           |
| `createdAt`   | string (ISO 8601 timestamp)   | Set on create, read-only                                     |
| `updatedAt`   | string (ISO 8601 timestamp)   | Set on create, refreshed on every update, read-only          |

## Endpoints

| Method        | Path             | Description                                   | Success                  |
| ------------- | ---------------- | --------------------------------------------- | ------------------------ |
| `POST`        | `/todos`         | Create a todo                                 | `201` + object + `Location` header |
| `GET`         | `/todos`         | List todos, optional `?state=todo\|doing\|done` | `200` + array            |
| `GET`         | `/todos/{id}`    | Get one todo                                  | `200` + object           |
| `PUT`/`PATCH` | `/todos/{id}`    | Update one or more fields (partial body is fine) | `200` + full object   |
| `DELETE`      | `/todos/{id}`    | Delete a todo                                 | `204` (no body)          |

### CSV output

`GET /todos` supports content negotiation with the `Accept` header:

| Accept header                          | Response                                       |
| -------------------------------------- | ---------------------------------------------- |
| missing, `*/*` or `application/json`   | `200`, JSON array (default)                    |
| `text/csv`                             | `200`, `Content-Type: text/csv; charset=utf-8` |
| anything else (e.g. `application/xml`) | `406 Not Acceptable`                           |

Quality values are respected (`Accept: application/json;q=0.5, text/csv;q=0.9` returns CSV), and the response carries `Vary: Accept`. The `?state=` filter works for both formats.

```http
GET /todos?state=done
Accept: text/csv
```

```
id,title,description,state,dueDate,createdAt,updatedAt
3f0c5c1e-...,Write API documentation,"OpenAPI + README examples, with a comma",done,,2026-11-25T16:00:00.000Z,2026-11-25T16:10:00.000Z
```

The conversion is `toCsv()` in `src/csv.js`. It follows RFC 4180: fields with commas, quotes or line breaks are quoted with inner quotes doubled, and empty values (`null`) are written as empty fields.

`PUT` accepts a partial body, as in the assignment example (`{ "state": "doing" }`), and always responds with the complete updated object. `PATCH` is routed to the same handler. To clear an optional field, send it as `null`.

### Examples

```http
POST /todos
Content-Type: application/json

{ "title": "Write API documentation", "description": "OpenAPI + README examples", "state": "todo" }
```

```http
HTTP/1.1 201 Created
Location: /todos/3f0c5c1e-8f7a-4a43-9d57-0c3a1d9f2a11

{
  "id": "3f0c5c1e-8f7a-4a43-9d57-0c3a1d9f2a11",
  "title": "Write API documentation",
  "description": "OpenAPI + README examples",
  "state": "todo",
  "dueDate": null,
  "createdAt": "2026-11-11T17:00:00.000Z",
  "updatedAt": "2026-11-11T17:00:00.000Z"
}
```

```http
PUT /todos/3f0c5c1e-8f7a-4a43-9d57-0c3a1d9f2a11
Content-Type: application/json

{ "state": "doing" }
```

Returns `200` with all attributes of the todo and a new `updatedAt`.

## Validation and error handling

All client errors return JSON in the same shape:

```json
{
  "error": "Bad Request",
  "message": "Validation failed",
  "details": ["state must be one of: todo, doing, done"]
}
```

| Status | When                                                                                                         |
| ------ | ------------------------------------------------------------------------------------------------------------ |
| `400`  | Malformed JSON; body is not a JSON object (array, string, missing); missing/empty/non-string `title`; invalid `state`, `description` or `dueDate`; unknown or read-only field in the body (`id`, `createdAt`, ...); empty update body; invalid `?state=` filter |
| `406`  | `GET /todos` with an `Accept` header that allows neither `application/json` nor `text/csv`                    |
| `404`  | No todo with the given id (`GET`, `PUT`, `PATCH`, `DELETE`), or an unknown route                              |
| `405`  | Known path with an unsupported method (e.g. `DELETE /todos`); the `Allow` header lists the valid methods     |
| `415`  | `POST`/`PUT`/`PATCH` with a body whose `Content-Type` is not `application/json`                              |
| `500`  | Unexpected server error (a generic message is returned, details are only logged)                              |

Notes:

- For `PUT`/`PATCH`, the existence of the todo is checked first (`404`), then the body is validated (`400`).
- A rejected update never changes the stored todo.
- Header variables in use: `Content-Type: application/json` on all bodies, `Location` on `201`, `Allow` on `405`.

## API documentation (OpenAPI)

The API is described in [`openapi.json`](openapi.json) (OpenAPI 3.0.3) and rendered with `swagger-ui-express` at **http://localhost:3000/doc**.

- The `servers` entry is `http://localhost:3000`, so every operation can be run from the page with **Try it out** (start the server first).
- Each operation lists its parameters, request body (with a ready-made example), and all responses: success codes and the client errors 400, 404, 406 and 415. Reusable parts (`Todo`, `NewTodo`, `UpdateTodo`, `Error`, shared error responses) live under `components`.
- For `GET /todos` the response media-type dropdown switches between `application/json` and `text/csv`, and the `state` parameter is a dropdown of the three allowed values.
- No authentication is documented because the API has none.
- Mounting is in `src/docs.js`; `createApp({ docs: false })` turns it off.

## Testing

### Manual requests (VS Code REST Client)

Install the **REST Client** extension (`humao.rest-client`), start the server with `npm start`, open [`requests.http`](requests.http) and click *Send Request* above any request. The file contains every happy path (create, list, filter by each state, get, `PUT`, `PATCH`, delete) and 18 client-error requests (`E1`-`E18`). The id of the created todo is captured automatically and reused by the later requests.

### Automated tests

Tests use Node's built-in test runner (`node:test`) and `fetch`, so no extra test dependencies are needed.

**Unit tests** (`test/unit/`) test single modules without HTTP or a running server:

| File                  | What it tests                                                                 |
| --------------------- | ----------------------------------------------------------------------------- |
| `validation.test.js`  | `isValidState`, `isValidDueDate` (leap days, impossible dates, bad formats) and `validateTodoInput` for create and update: valid input, every invalid case, error messages, multiple errors at once |
| `todoService.test.js` | create / list / get / update / remove with a **fixed clock and fixed ids**, so exact timestamps and ids are asserted; `ValidationError` and `NotFoundError` cases; "404 before 400" ordering; rejected updates leave data unchanged; a fake store proves the service really uses the injected store |
| `csv.test.js`         | `escapeField` and `toCsv`: header, exact rows, null values, commas / quotes / line breaks, column count matches the header |
| `openapi.test.js`     | the OpenAPI document: every endpoint documented, unique operationIds, all `$ref`s resolve, success and error codes present, request examples present |
| `todoStore.test.js`   | the in-memory store: insert, find, replace, remove (first/middle item), copy-safety of `all()` |

**Integration tests** (`test/integration/`) start the real Express app on a random port and send real HTTP requests:

| File              | What it tests                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| `api.test.js`     | Every endpoint: happy paths, status codes, response bodies and headers, and all client errors (400, 404, 405, 415) |
| `csv-and-docs.test.js` | `Accept` negotiation on `GET /todos` (CSV, JSON, default, `*/*`, q-values, 406, 400 with CSV), CSV escaping end to end, `/doc` and `/doc/openapi.json`, and that the documented examples really work |
| `routes.test.js`  | A complete create -> read -> update -> filter -> delete lifecycle with exact values; instance isolation; the HTTP layer alone with a **stubbed service** (correct arguments passed on, `ValidationError` -> 400, `NotFoundError` -> 404, unexpected error -> 500 without leaking details, service not called for 415/malformed JSON) |

Every test gets its own app and empty data store, so tests do not depend on each other or on execution order.

## Refactoring for testability

The original `app.js` was one file in which validation, business logic and Express routes were mixed together. I only changed what made testing hard:

| Problem found                                                                 | Change                                                                 |
| ----------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Validation was only reachable through HTTP requests                           | Moved to `src/validation.js` as pure functions (no Express, no I/O)    |
| Business logic lived inside the route handlers                                | Moved to `src/todoService.js`; routes are now 2-3 lines each            |
| `new Date()` and `randomUUID()` were called directly, so values were unpredictable | The service receives `now` and `generateId` as parameters (real ones by default) |
| The data array was a hidden variable inside the app                           | Moved to `src/todoStore.js` behind a tiny interface the service receives as a parameter |
| Errors were turned into HTTP responses all over the place                      | The service throws `ValidationError` / `NotFoundError` (`src/errors.js`); one error handler in `app.js` maps them to 400 / 404 |
| Tests could not replace the service                                           | `createApp({ service })` accepts a service, so the HTTP layer can be tested alone |

The HTTP behaviour did not change: the 63 tests written before the refactoring passed unchanged afterwards.

## Report and reflection

### What was built

All endpoints from the assignment are implemented (`POST`, `GET` list with `?state=` filter, `GET` by id, `PUT` plus `PATCH`, `DELETE`), together with validation of every input, JSON error responses and appropriate status codes. The `requests.http` file exercises every endpoint and every error case, and the automated suite (174 tests) checks the same behaviour.

### Design decisions

- **Partial `PUT`.** The assignment's example sends only `{ "state": "doing" }` and expects the full object back, so `PUT` merges the supplied fields into the existing todo. Strict "replace the whole resource" semantics would have made that example fail with a `400`.
- **Strict bodies.** Unknown and read-only fields (`id`, `createdAt`, `updatedAt`) are rejected with `400` instead of being silently ignored, so a typo like `"stat": "done"` is reported rather than lost.
- **404 for any unknown id.** `GET /todos/1000` returns `404`, as the assignment says, rather than `400` for "not a UUID". From the client's point of view the resource simply does not exist.
- **Timestamps** are ISO 8601 strings and the field is called `updatedAt`, following the suggested data model.
- **IDs** are generated with Node's built-in `crypto.randomUUID()`, which produces the same v4 UUIDs as the `uuid` package without an extra dependency.

### Problems and things I noticed

- The two array snippets in the hints contain bugs. `data.find(...)` returns the item itself, not an array, so `filtered[0]` would be `undefined`. And `data.splice(fid, fid)` removes `fid` elements, which only deletes one item when `fid` is 1 (and nothing when it is 0). The correct call is `splice(index, 1)`. A test that deletes the *middle* of three todos and checks the other two survive guards against this class of bug.
- Validation took more thought than the happy paths: deciding what counts as a valid `dueDate` (including rejecting impossible dates like `2026-02-30`), distinguishing `400` from `415` from `404`, and checking for the todo's existence before validating the body.
- A missing body behaves differently from a malformed one in Express, so both cases have their own test.

### Testing reflection

- The biggest win was injecting the clock and id generator. Before, a test could only check that `createdAt` "looks like a date"; now it can assert the exact value and that `updatedAt` changes on update but `createdAt` does not.
- Splitting validation out turned dozens of HTTP round trips into fast function calls, so edge cases (leap days, `2026-02-30`, whitespace titles) are cheap to cover. The integration tests then only need to prove that the layers are wired together.
- Testing the routes with a stub service found a case the old tests could not reach: an unexpected error must give a generic `500` and must not leak the original message.
- Coverage (`npm run test:coverage`) is 100% for everything in `src/`. The remaining uncovered lines in `app.js` are the `413 Payload Too Large` branches, which need a request body over Express's size limit.
- Test order independence matters: creating a new app per test avoided shared state, which is the most common cause of flaky tests.

### OpenAPI and CSV reflection

- Writing the spec first-hand exposed gaps: I had to decide and document what `GET /todos` returns for an unsupported `Accept` header (`406`), and that the update body needs at least one field.
- A test checks that the examples in the spec really work against the running app, so the documentation cannot silently drift from the code.
- The `toCsv` example in the assignment writes `description` in each row but not in the header, prints `null` for a missing description, and does not escape quotes or commas, which breaks the row whenever a title contains one. `src/csv.js` fixes all three.
- CSV files opened in a spreadsheet can treat cells starting with `=`, `+`, `-` or `@` as formulas. This API returns the stored text unchanged; a production system exporting untrusted text should neutralise such cells.

### What I would do next

- Persist data in a database (SQLite or MongoDB) instead of an array.
- Add pagination and sorting to `GET /todos`.
- Document the API with an OpenAPI/Swagger file.
- Add authentication and per-user todo lists.
